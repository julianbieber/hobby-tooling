# hatlas

| Field        | Value                                                                  |
| ------------ | ---------------------------------------------------------------------- |
| Type         | CLI                                                                    |
| Binary       | `hatlas`                                                               |
| Owner        | @julianbieber                                                          |
| Dependencies | `cargo`, a nightly toolchain (rustdoc JSON is nightly-only), `rust-analyzer` on it |
| Status       | experimental                                                           |

## Description

A Bevy workspace's plugins, components, resources, systems and observers as linked local
HTML pages, built from rustdoc JSON, a rust-analyzer SCIP index and the workspace source.

```
hatlas <repo dir> [--out <dir>]
```

- **Builds the target workspace.** A run executes its build scripts and proc macros, as
  `cargo build` does. Do not point it at a repo you would not build.
- **Toolchain.** `rustc -vV` runs in the repo; a nightly there is used as is. Otherwise every
  cargo call is `+nightly`, into `<target>/hatlas-nightly` so the cache never collides with the site.
- **Systems.** Every `add_systems`, `configure_sets`, `add_observer`, `add_plugins` and
  `init_resource` / `insert_resource` call is read from source by method name, then each name in
  it is resolved through `rust-analyzer scip`. A system or observer page shows its parameters
  (a `Query`, `Single` or `Populated` split into data and filters), and per registration the
  schedule, own run conditions, conditions inherited through the sets it is in, ordering, call
  site and the plugin or function that registered it. A function passed to `add_plugins` becomes
  a plugin; a closure is an anonymous system on its module's page. Registrations that cannot be
  attributed are listed on the index.
- **Events.** Every event type the workspace reads, writes, triggers or observes has a page: the
  item's own page when the workspace defines it, otherwise `events/<crate>/event.<Name>.html`,
  naming the defining crate. Producers are writer parameters and `trigger` / `trigger_targets` /
  `write_message` / `send_event` calls (`send` and `write` only for types already known as events);
  listeners are reader parameters and functions or closures whose first parameter is `On<E>` /
  `Trigger<E>`. Each links to its page, or its module's anchor, with the call site. Dependency bodies
  are never read, so an event triggered only inside a dependency lists no producer. A function with an
  `On<E>` first parameter is an observer even when no registration is found. Known gap: an observer
  or trigger inside a macro (`bsn!`'s `on(...)`) is seen only through the function's signature.
- **Dependencies.** Every dependency item the workspace references directly has a page under
  `deps/<package>-<version>/` with its rustdoc and the workspace files that use it, each linking
  to that file's module page. Only packages SCIP sees referenced are documented, public items
  only, in one keep-going `cargo doc --no-deps`. A package that fails to document is named under
  *Undocumented crates* on the index and the run still writes a site. Of two versions of one
  crate the most-referenced is documented. std, core and alloc are plain text. Symbols that match
  no rustdoc item are listed as plain text under *Unmapped symbols*; modules are not pages. On a
  cargo without `cargo doc --output-format` the JSON comes from `RUSTDOCFLAGS`, which
  re-documents every referenced dependency on every run.
- **SCIP cost.** `rust-analyzer scip` builds the workspace and took about 3.5 GB of memory on
  a large game. A stable repo runs it under `+nightly` in `<target>/hatlas-nightly`.
- **Known gap.** Registrations generated by a macro are invisible to the source reader; only a
  macro written inside a registration call is listed as unresolved.
- **Output.** `<target>/hatlas/index.html`, or `--out`. The index lists public modules, plugins,
  components and resources per crate. A module's page lists its own items, private ones included,
  and each plugin, component and resource has a page with its rustdoc.
- **Links are a hard check.** A page that links to something the site does not contain fails the
  run. Doc-comment links that resolve to nothing in the site are shown as plain text.
- **The swap.** The site is written next to its destination, link-checked, then replaces the old
  one. A directory without the `.hatlas-site` marker is never replaced; the run stops with an error
  before compiling anything.
- **Supported `format_version`s:** 57 and 61. Any other fails naming the version. To add one, add a
  toolchain to the `fixtures` recipe in `justfile`, run `just fixtures`, and add the version to
  `SUPPORTED` in `src/rustdoc.rs`.
- **Vendored.** `assets/cytoscape.min.js` is cytoscape.js 3.30.4 (MIT, `assets/LICENSE`) from
  `https://registry.npmjs.org/cytoscape/-/cytoscape-3.30.4.tgz`, sha256
  `1bb5340e549511e111b31e5684872c949ad33d40ea5dba0ad8e7d90c62c7b3b9`; `just vendor-check` verifies it.
- **Graph.** The index opens with a pan-and-zoom graph: nodes are the public plugins, components,
  resources, events, systems and observers plus one per documented dependency crate; edges are
  registrations, event producers and listeners, and file-level uses of a crate. The `breadthfirst`
  layout is rooted at the plugins and computed in the browser. The data is `graph-data.js`, a script,
  because `fetch` of a sibling file is blocked under `file://`. A click opens the node's page, and every
  node's link is part of the hard check.
