Answer $ARGUMENTS (or, when invoked by description rather than `/research`, my
last message) as a fixed-shape markdown file, never prose. This is research on
the side of a jam entry where LLM-written code and assets are prohibited, so
nothing here may write code or copy text into the jam repo — only files in
this task's `research/` dir.

## 0. Pick the shape

`hresearch new "<question verbatim>"` decides the shape and reports it on
stderr as `shape: <x> (from question)` — that is the shape this question is
answered in, and `hresearch render` refuses a card in any other shape. A
question asking which techniques, approaches or options exist for a problem
— a survey of alternatives ("which techniques exist to …", "what approaches
are there for …") — is an **option-matrix**. A question asking how a
technique, algorithm or mechanism works internally ("how does a flow field
pathfinder move many agents", "how does X work") is a **mechanism-figure**.
Anything else — "how do I use this API", "what does this function do" — is an
**answer-card**. Everything below step 0 is common to all three; where they
differ it says which shape it's for.

Pass `--shape card|matrix|figure` on `new` only when the classifier's guess
plainly contradicts what the question is actually asking (e.g. "what options
does this function take" is an API question, not a survey — `--shape card`);
judge the override against the same three definitions above, since that is
what `render` will hold the answer to.

1. `hresearch new "<question verbatim>"` first, once per question — never
   render a later question into an earlier question's dir, and never pass a
   dir this command did not just print in this task. Its stdout is the
   sources dir — every other `hresearch` call in this run takes that path.
2. Search with `WebSearch`. Every page you intend to cite is fetched with
   `hresearch fetch <dir> <url>` — never `WebFetch` for a page you'll cite,
   because a cited quote or precedent has to be checkable against the stored
   copy `fetch` makes. Read or `Grep` the stored `<id>.txt` files to find the
   sentences and code you need.
3. Prefer docs.rs (or the crate's own docs) for API facts, and a GitHub `blob`
   link into the crate's `examples/` or source for a card's snippet or a
   matrix's precedent.

A `render: shape: the question called for <x>, got <y>` error means the JSON
you sent is in the wrong shape for what this question was recorded as — fix
the JSON to answer in shape `<x>` and render again. Never re-run `new` to get
a different shape than the one it already picked; that is what `--shape` on
the original `new` call is for.

## Answer-card

4. Fill the slots:
   - **verdict** — 1–2 items, the answer itself.
   - **how** — up to 6 numbered steps.
   - **snippet** — one contiguous block copied verbatim from a fetched
     example or source, never written or edited by you, not even a rename.
   - **breaks** — the source's own sentences about a pitfall or caveat, not
     your paraphrase of it.
   - **source** — generated by the tool; you never write it.
   Every item is a fragment under 160 characters, never a paragraph. A claim
   with no fetched source backing it carries no `src` and renders
   `[unsourced]` — never state it as if it were sourced. A slot with nothing
   honest to put in it is `{"empty": "<why>"}`.
5. Render:
   ```
   hresearch render <dir> - <<'JSON'
   { "verdict": [...], "how": [...], "snippet": {...}, "breaks": [...] }
   JSON
   ```
   A `render:` error names the slot and the problem — fix the JSON (drop or
   re-copy the offending text, mark it unsourced, or empty the slot) and
   render again. Never write `card.json` or the `.hresearch` by hand, and never
   touch the jam repo checkout.
6. Reply in the pane with exactly one line: the card's path. Nothing else —
   the card is the answer, not a summary of it.

## Option-matrix

4. Pick 2–5 techniques as columns — never more than 5; if more are genuinely
   candidates, keep the strongest ones and drop the rest.
5. The four criteria are fixed and every cell must be filled for every
   column, in a few words, never a sentence:
   - **looks like** — what it produces or feels like in play.
   - **cost per frame** — the shape of its runtime cost.
   - **jam-sized** — whether it fits a jam's time and scope, and the catch if
     any.
   - **bevy precedent** — for each technique, `hresearch fetch` a Bevy
     example, crate or repo that implements it and cite it as `{"src": k}`;
     `{"none": true}` when no precedent was found. Never a `text` cell here.
6. `verdict` names exactly one column — pick one, never "it depends".
7. Render:
   ```
   hresearch render <dir> - <<'JSON'
   { "shape": "matrix",
     "options": [ {"name": "...", "cells": {
         "looks like": {"text": "...", "src": 1},
         "cost per frame": {"text": "..."},
         "jam-sized": {"text": "..."},
         "bevy precedent": {"src": 2} } }, ... ],
     "verdict": {"option": "...", "text": "..."} }
   JSON
   ```
   A `render:` error names the cell and the problem (too many words, an
   unknown criterion, a verdict naming no column, a precedent cell with no
   `src` or `none`) — fix the JSON and render again. Never write `card.json`
   or the `.hresearch` by hand.
8. Reply in the pane with exactly one line: the matrix's path.

## Mechanism-figure

4. `hresearch fetch` the source that explains the mechanism — a paper,
   article, docs page or reference implementation.
5. Draw the mechanism as an ASCII figure: its stages left to right or top to
   bottom, joined by arrows (`───►`, `→`, `↓`), each stage a small box or grid
   showing the data it holds. Labels are at most 5 words each, never a
   sentence — draw the mechanism, don't caption each piece of it. Enough
   detail that someone could implement from the figure alone, at most 78
   columns and 30 lines.
6. Write one caption line (≤ 16 words) with a `src` — the single sentence the
   figure itself can't show.
7. Render:
   ```
   hresearch render <dir> - <<'JSON'
   { "shape": "figure",
     "figure": "line one\nline two\n...",
     "caption": {"text": "...", "src": 1} }
   JSON
   ```
   `figure` may also be a JSON list of line strings. A `render:` error names
   the line or the caption and the problem (a line too wide, a word run that
   reads as prose, no drawing character anywhere, a caption with no `src` or
   more than one line) — fix it and render again. Never hand-write the figure
   around a rejection; redraw it. Never write `card.json` or the `.hresearch` by
   hand.
8. Reply in the pane with exactly one line: the figure's path. The figure is
   a notes file — it never gets written into the jam repo — and a throwaway
   interactive visual (a plot, a live viewer) is allowed alongside it but is
   never the default medium; the figure is the answer.
